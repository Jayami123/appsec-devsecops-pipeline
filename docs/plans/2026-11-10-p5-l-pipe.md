## 5. Per-scanner specification

Common rules for every L-PIPE scan job:

- `runs-on: ubuntu-latest`; `timeout-minutes: 20` (MP:655, provisional) unless stated.
- `permissions: contents: read` at job level, except the two upload jobs (section 5.1).
- No `continue-on-error`. `if: always()` appears only on the summary and gate jobs and on the ZAP harness-teardown step (section 5.8).
- No `secrets:` key for any scan job (MP:666 caller; scanners need none).
- Every external `uses:` is a full 40-hex SHA with a version comment (MP:689). The only external actions are `github/codeql-action/*` (section 5.5) and the already-pinned `actions/checkout` (MP:691). The other tools (gitleaks, OSV-Scanner, Trivy, Syft, zizmor, actionlint) are binaries or wheels fetched and verified by `scripts/scan/fetch-tool.sh` or a hash-pinned pip requirement, so they have no `uses:` line.
- Verdict to the gate: exactly one of `pass`, `fail`, `not-implemented` (MP:749). A stub never emits `pass` (MP:749).
- Exit codes are never the verdict by themselves. The threshold script reads the tool output (section 6).

#### 5.2.1 `config/scan/gitleaks.toml` (exact structure)

```toml
title = "P5 gitleaks config: this repository only (exact-line entries)"

[extend]
useDefault = true

# One entry per PR #3 allowlist row (16 rows). Each entry: regexTarget "line", one path, one anchored line.
# Row text is copied verbatim from the PR #3 body; regex metacharacters are escaped by the build.
[[allowlists]]
description = "PR #3 row 1: src/kit/env.ts:71 (loopback default, public local value, not a secret)"
regexTarget = "line"
paths = ['''src/kit/env\.ts$''']
regexes = ['''^<verbatim line 71, escaped>$''']

# ... rows 2-16 in the same shape ...

# Row 17 (ONLY if the owner approves STOP-A): tests/unit/security/redact.test.ts:12 (synthetic redaction input).
```

Rules enforced by a test (section 5.11):
- every `[[allowlists]]` entry has `regexTarget = "line"`, exactly one entry in `paths`, and every regex starts with `^` and ends with `$`;
- no `stopwords`, no `commits`, no `[allowlist]` table, no entry with a path glob wider than one file;
- the entry count equals the owner-approved count (16, or 17 with STOP-A).

Verified by the probe (probe section 2c): exact-line suppression works, the same line in another path is still reported, and `[[allowlist]]` (singular) fails to load. The line-changed negative control was inconclusive (PARTIAL).

### 5.12 TypeScript skeletons (threshold core and one test)

`scripts/scan/threshold-core.ts` (skeleton; the build completes it and its tests):

```ts
// Verdict contract for every L-PIPE scanner (MP:749, MP:751-757).
export type Verdict = "pass" | "fail" | "not-implemented";
export type Severity = "CRITICAL" | "HIGH" | "MEDIUM" | "LOW" | "UNKNOWN";

export interface ScanOutcome {
  readonly verdict: Verdict;
  readonly reason: string;
  readonly blocking: readonly string[];   // fingerprints only; never message text
}

export function normalizeSeverity(raw: string | undefined): Severity {
  switch ((raw ?? "").toUpperCase()) {
    case "CRITICAL":
      return "CRITICAL";
    case "HIGH":
      return "HIGH";
    case "MEDIUM":
    case "MODERATE": // OSV uses MODERATE; Trivy uses MEDIUM (probe 2d)
      return "MEDIUM";
    case "LOW":
      return "LOW";
    default:
      return "UNKNOWN";
  }
}

export function failClosed(reason: string): ScanOutcome {
  return { verdict: "fail", reason, blocking: [] };
}

// Expired baseline or accepted-risk entries count as NEW (MP:684).
export function isExpired(expiresIso: string, nowIso: string): boolean {
  return Date.parse(expiresIso) < Date.parse(nowIso);
}
```

`scripts/scan/codeql-threshold.ts` (skeleton; reads rule severity, not result level):

```ts
import { readFileSync } from "node:fs";
import type { ScanOutcome } from "./threshold-core.ts";
import { failClosed } from "./threshold-core.ts";

const OWNED_PREFIXES = ["src/", "scripts/", "tests/", ".github/"] as const; // D4 (MP:682)

export function evaluateCodeql(sarifPath: string, baseline: ReadonlySet<string>, nowIso: string): ScanOutcome {
  let doc: any;
  try {
    doc = JSON.parse(readFileSync(sarifPath, "utf8"));
  } catch {
    return failClosed("unreadable SARIF");
  }
  const run = doc?.runs?.[0];
  if (!run || run.invocations?.[0]?.executionSuccessful !== true) {
    return failClosed("SARIF without a successful invocation"); // NEW-PIPE-2
  }
  const blocking: string[] = [];
  for (const result of run.results ?? []) {
    const rule = run.tool.driver.rules[result.ruleIndex];
    const sev = Number(rule?.properties?.["security-severity"]); // level is absent (probe 2b)
    const uri: string = result.locations?.[0]?.physicalLocation?.artifactLocation?.uri ?? "";
    const hash: string = result.partialFingerprints?.primaryLocationLineHash ?? "";
    const fp = `${result.ruleId}|${uri}|${hash}`;
    const owned = OWNED_PREFIXES.some((p) => uri.startsWith(p));
    if (sev >= 7.0 && owned && !baseline.has(fp)) blocking.push(fp); // High or Critical, NEW, owned, fix by definition (MP:683)
  }
  return blocking.length === 0
    ? { verdict: "pass", reason: "no NEW High or Critical in owned code", blocking }
    : { verdict: "fail", reason: "NEW High or Critical in owned code", blocking };
}
```

## 6. Threshold semantics (per tool) and verdict mapping

Common (applies to every tool; probe section 2b):

1. The gate reads the tool's output file, not the exit code alone. A missing file, an unparseable file, a missing invocation or an exit code outside the documented clean and findings values is `fail` (NEW-PIPE-2).
2. A tool error in a report-only job is still `fail`. Report-only means the findings do not block; it does not mean the tool may fail silently.
3. `pass` requires the output to be parsed and every finding to be classified.

### 6.1 gitleaks (blocking, this repo)

- Blocking set: every finding not allowlisted by `config/scan/gitleaks.toml`. Any remaining finding is `fail`.
- Accepted risks do not suppress a gitleaks finding (a secret is removed or allowlisted by line, not accepted).
- Verdict: exit 0 and parsed JSON with zero findings = `pass`; exit 1 and parsed JSON with at least one finding = `fail`; anything else = `fail`.

### 6.2 Trivy (report-only images and forks; gating root filesystem)

- Fingerprint (for the baseline): `VulnerabilityID|PkgName|InstalledVersion|Target`.
- Owned: `Target` equals `package-lock.json` (the repository's own dependency tree). Fork and image targets are not owned.
- Fix available: `FixedVersion` is a non-empty string.
- Blocks when: NEW (not in `config/scan/baseline/trivy.json` or the entry expired) and owned and `Severity` is `HIGH` or `CRITICAL` and fix available.
- Verdict: `pass` when nothing blocks; `fail` when something blocks, or on tool error.
- Images and forks: their verdict is `pass` or `fail` on tool error only; findings are reported in the summary and do not block.

### 6.3 OSV-Scanner (gating root lockfile; report-only forks)

- Fingerprint: `id|package.name|package.version|source.path`.
- Severity: `database_specific.severity` normalised by `normalizeSeverity` (MODERATE = MEDIUM); missing or `UNSPECIFIED` is `UNKNOWN` (not blocking).
- Fix available: any `affected[].ranges[].events[]` with a `fixed` key for the matched package (probe 2b structure).
- Owned: `source.path` equals `package-lock.json`.
- Blocks when: NEW and owned and severity HIGH or CRITICAL and fix available.
- Current result on main: one MEDIUM (`GHSA-g3hv-75wg-m249`, fixed 11.0.1): not blocking.

### 6.4 npm audit (gating root lockfile)

- Fingerprint: `<name>|<via.source>|<via.range>`, taken from the advisory object in `via`. Transitive `via` entries (strings) are followed to their advisory object (probe 2c; only one root-level advisory object was present, for `minimatch`).
- Severity: `vulnerabilities[name].severity` (`critical`, `high`, `moderate`, `low`).
- Fix available: `fixAvailable` is truthy. A `fixAvailable` object with `isSemVerMajor: true` counts as fix available and is labelled in the summary (probe 2c: all 7 object fixes on main are major; they propose older versions and need a human decision).
- Owned: the root `package-lock.json` (`isDirect` is not used).
- Blocks when: NEW and owned and severity high or critical and fix available.
- Current result on main: 10 moderate, all dev-only, none high or critical: not blocking. They stay open and are not accepted (D4; no accepted-risk entry).

### 6.5 CodeQL (PN-4; MP:679-686)

- Severity: `rules[ruleIndex].properties["security-severity"]` (string, parsed as a number). Critical at 9.0 or above; High at 7.0 or above. `level` is absent on CodeQL results (probe 2b) and is not used.
- Newness: fingerprint `ruleId|uri|partialFingerprints.primaryLocationLineHash` not in `config/scan/baseline/codeql.json` (or entry expired).
- Ownership: `uri` starts with `src/`, `scripts/`, `tests/` or `.github/` (MP:682).
- Fix available: true by definition for owned code (MP:683; correction 13).
- Accepted risks: suppressed only by an unexpired `accepted_risks` entry with a matching fingerprint (section 7.4; MP:684). The schema needs a match field (section 7.4, owner decision).
- Verdict: `fail` if any NEW, owned, High or Critical result is unsuppressed; otherwise `pass`. Upload success is never the gate (MP:685).
- Current result on main (probe 2c): `js/incomplete-sanitization` (`src/kit/ci/playwright-json-summary.ts:183`) is a true positive at 7.8 (blocks until fixed or accepted); `js/regex/missing-regexp-anchor` (`tests/unit/kit/import-closure.test.ts:53`) is a false positive at 7.8 (blocks until baselined by owner review).

### 6.6 zizmor (PN-6, blocking on errors)

- Blocks when: any SARIF result with `level` `error`.
- Warnings are reported in the summary and do not block.
- Exit code is not used for the verdict (zizmor exits 0 with findings, RECORDED-2). Exit 1 or 3 is `fail` (3 means no inputs; a workflow directory with no workflows is `fail`, since the gate must see real input).

### 6.7 ZAP (report-only; D11)

- Verdict: `pass` when the baseline ran, produced parseable JSON and the stack was torn down. `fail` on a crash, a timeout, malformed or missing JSON, or a stack that did not stop.
- Alerts never change the verdict. Alerts at High and above are written to the summary; a finding worth tracking becomes a `findings[]` entry only by an owner decision (MP:597 and the ledger rules).
- Authenticated mode: `not-implemented` until the login helper merges (MP:337).

### 6.8 syft (PN-5) and summary (SCAN-005)

- Syft: section 5.7.
- Summary: no verdict of its own. A missing scanner row fails the summary, and the gate reads the scanner rows.

### 6.9 Gate reading (F0-3 contract, MP:667) and registry flips (MP:751, MP:757)

The gate reads `codeql_verdict` and `scanner_status` (a JSON object, one key per registry name, values `pass`, `fail` or `not-implemented`). It fails when: a key with registry value `implemented` is `not-implemented`; any value is `fail`; a `stub` key reports `pass` or `fail` (MP:756, rejected by the registry test). A stub that is `not-implemented` passes with a `NOT IMPLEMENTED` row (MP:754).

Registry flips: each implementing PR changes its own key in `config/scan/implementation-status.json` from `stub` to `implemented` in the same PR (MP:751). A PR that flips a key without its job (or leaves a stub marker on the job) fails `registry.test.ts`. Section 11 lists the flip in each PR.

## 7. Baseline, accepted risks and enforcement

### 7.1 Baseline format (correction 6)

Path: `config/scan/baseline/<tool>.json` for `codeql`, `trivy`, `osv` and `npm-audit`. Schema (validated by `tests/unit/scan/baseline.test.ts`):

```json
{
  "schema": 1,
  "tool": "codeql",
  "entries": [
    {
      "fingerprint": "js/regex/missing-regexp-anchor|tests/unit/kit/import-closure.test.ts|<primaryLocationLineHash>",
      "ruleId": "js/regex/missing-regexp-anchor",
      "path": "tests/unit/kit/import-closure.test.ts",
      "justification": "<one sentence: why this result is a false positive or accepted-as-known>",
      "owner": "the owner",
      "reviewRef": "<owner review reference on the PR>",
      "addedOn": "YYYY-MM-DD",
      "expires": "YYYY-MM-DD"
    }
  ]
}
```

Rules:
- `expires` at most 90 days after `addedOn` (MP:657). The schema test rejects longer.
- An expired entry is NEW.
- A baseline entry that matches no current result is stale. Stale = `fail` for that tool until the entry is removed in the same PR that fixed the alert (NEW-PIPE-3).
- `owner` is a role ("the owner"), never a personal name (MP:602).
- The probe shows the initial baselines are empty for `trivy`, `osv` and `npm-audit` (no owned High or Critical with a fix on main) and hold one CodeQL entry (the false positive) only after owner review. The true positive is fixed in a foundation PR, not baselined.

### 7.2 Baseline change review

- Each baseline change is its own PR (correction 3). Builders do not approve their own baseline change.
- The owner's required review on `config/scan/baseline/` is an owner ruleset or CODEOWNERS action (section 9). The code cannot prove reviewer identity; the test in 7.1 checks every field is present, and the owner review is the control.
- Tampering control: a PR that adds a fingerprint without the fields fails `baseline.test.ts`. A PR that adds a fingerprint with fields but without owner review is a process failure the owner catches at review (stated limit).

### 7.3 Enforcement limit (stated)

Nothing in the code proves that a reviewer approved a baseline line. The plan relies on the owner's review, the field checks, and the same-PR stale rule. This is recorded as a limit, not a control.

### 7.4 Accepted risks (from the F0-4 ledger)

- Entry fields (F0-4 schema, MP:596-597): `id`, `product`, `status: "accepted-risk"`, `title`, `severity`, `owner`, `reason`, `acceptedOn`, `expires`.
- Required: `owner` (non-empty), `reason` (non-empty), `expires` (ISO date, at most 90 days after `acceptedOn`). Expired entries fail the gate (MP:597, MP:684).
- Owner decision needed (correction, not in the master plan): the schema has no match key, so the threshold cannot tie an accepted risk to a fingerprint. Proposal: add `match: { tool: string, fingerprint: string }` to `accepted_risks[]` in a foundation PR before any PN-4 suppression is used.
- Never fabricated: `accepted_risks` stays empty until the owner approves an entry (section 9).

### 7.5 Fork PRs (correction 9)

Recorded decision for this lane: fail-closed by design.

- On a fork PR, `p5-scans` is skipped by its same-repo `if:`. The gate sees a skipped scan job while `p5_scans` is true and fails (MP:665-667).
- A fork PR therefore cannot merge until the owner decides otherwise. This is the safe default.
- Owner option A (keep): nothing to change.
- Owner option B (fork-safe gitleaks): a `gitleaks` job on `pull_request` outside the same-repo condition, with `permissions: contents: read`, no `secrets:` and no checkout credentials persisted. It blocks a synthetic secret in a fork PR. This is a foundation `ci.yml` change (F0-3 owns it) and needs its own foundation PR. `pull_request_target` is not used (MP:725-726 test 6; GitHub docs warn about it, probe 2e).
- NEW-PIPE-6 covers the chosen option.
